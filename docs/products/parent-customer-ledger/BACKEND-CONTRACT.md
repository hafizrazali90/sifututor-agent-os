# API And Security Contract

## Public SIMS Endpoint

```http
GET /api/parent/payment-statement
Authorization: Bearer <existing-parent-sanctum-token>
X-Request-ID: <optional-client-correlation-id>
```

Query parameters:

| Field | Type | Rule |
| --- | --- | --- |
| `from` | `YYYY-MM-DD` | Optional inclusive local date; must be supplied together with `to`. |
| `to` | `YYYY-MM-DD` | Optional inclusive local date; must be supplied together with `from`. |
| `range` | `all` | Optional explicit all-history request; mutually exclusive with `from`/`to`. |
| `cursor` | opaque string | Optional; generated by server. |
| `limit` | integer | Optional, default 50, minimum 20, maximum 100. |

With no period parameters, the server returns the previous 12 months through
today. The app uses `range=all` for the All preset.

The parent ID is never accepted as an authorization parameter. SIMS derives it
from the authenticated parent.

### Enumerations

`type`:

- `invoice_charge`
- `payment`
- `commitment_fee_charge`
- `commitment_fee_payment`
- `refund_credit`
- `credit_application`
- `legacy_adjustment`

`direction`: `debit`, `credit`, `informational`.

`posting_status`: `posted`. V1 main-feed rows are finalized only.

`payment_status`: `completed` or `null`.

`timestamp_precision`: `second`, `date`, `unknown`.

`data_quality`: `complete`, `historical_missing_fields`, `legacy_derived`.

### Error Contract

| HTTP | Code | Meaning |
| --- | --- | --- |
| 401 | existing session-expired code | Parent token missing, expired, or invalid. |
| 422 | `INVALID_STATEMENT_FILTER` | Invalid date, `from > to`, bad cursor, or bad limit. |
| 503 | `STATEMENT_TEMPORARILY_UNAVAILABLE` | No complete response and no acceptable last-known-good cache. |

The 503 body must be app-safe and must not reveal Ripple or database details.

## Private Ripple Endpoint

```http
GET /api/internal/v1/parent-ledger?from=...&to=...&cursor=...&limit=...
Authorization: Bearer <short-lived-SIMS-service-JWT>
X-Request-ID: <correlation-id>
```

The path contains no parent ID. Ripple derives the parent from the signed
subject claim.

### Service Token

Use an asymmetric signing key so Ripple stores only a SIMS public key. Required
claims:

| Claim | Required value |
| --- | --- |
| `iss` | `sims` |
| `aud` | `ripple-parent-ledger` |
| `sub` | `parent:<SIMS parent id>` |
| `scope` | contains `parent-ledger:read` |
| `iat` | current issuance time |
| `exp` | no more than 120 seconds after `iat` |
| `jti` | unique token identifier |
| `request_id` | propagated correlation ID |

The JWT header includes `kid` for rotation. Ripple verifies algorithm, issuer,
audience, expiry, not-before when present, scope, subject format, and key ID.
Never accept `alg=none`, an unexpected algorithm, or a parent ID from an
unsigned query/header.

Ripple stores each accepted `jti` until token expiry and rejects replay. If SIMS
performs its one permitted connection retry, it signs a new token with a new
`jti` while preserving the correlation ID.

Recommended algorithm: Ed25519/EdDSA if supported consistently by the deployed
PHP and Node runtimes; otherwise RS256. The concrete choice is confirmed during
the preflight and documented before keys are generated.

### Proxy Boundary

`/api/internal/v1/` must not be added to Ripple's unauthenticated
`PUBLIC_PREFIXES`. Add a separate internal route class in `src/proxy.ts` which
performs service-token verification and denies all unrecognized internal routes.
The handler re-verifies or consumes only trusted claims passed by the proxy.

HTTPS is mandatory. Stable source-IP allowlisting, a private tunnel, or
Cloudflare Access may be added as defense-in-depth but cannot replace JWT
verification.

### Internal Response

Ripple returns the canonical shape plus internal source-completeness metadata.
SIMS strips fields not present in the public contract.

```json
{
  "contract_version": "1.0",
  "projection_complete": true,
  "generated_at": "2026-07-17T14:42:31+08:00",
  "source_freshness": {
    "sims_read_at": "2026-07-17T14:42:30+08:00",
    "ripple_read_at": "2026-07-17T14:42:31+08:00"
  },
  "statement": {}
}
```

If a required source fails, Ripple must not return `projection_complete=true`.
Prefer a non-2xx response so SIMS can use its last-known-good policy.

## Canonical Event Identity And Source Priority

| Event | Primary identity/source | Duplicate exclusion |
| --- | --- | --- |
| FIUU app payment | SIMS `parent_payment_attempts.id`, enriched by FIUU transaction ID | Group all attempt items; do not emit one SIMS payment per invoice. |
| Confirmed Ripple receipt | `customer_receipts.id` | Exclude linked `payment_records`. |
| Legacy manual payment | unlinked active `payment_records.id` | Include only when no canonical receipt/gateway payment represents it. |
| Invoice | SIMS `parent_invoices.id` | Payable base is `amount_due`, with documented legacy fallback. |
| Commitment fee | SIMS commitment-fee ID | Produce linked charge/payment effects once. |
| Refund credit | SIMS refund ID | Never also emit a cash refund without transfer evidence. |
| Credit application | Ripple application ID | Zero balance delta if the source receipt/payment is already represented. |

Stable IDs are prefixed, opaque strings. They are safe for React keys and cursor
construction but are not authorization tokens.

## Cache And Timeout Contract

- Ripple live-query timeout budget: target 1.0 second, hard cap agreed during
  implementation based on current infrastructure.
- SIMS-to-Ripple total timeout: lower than the parent API gateway timeout and no
  uncontrolled retries.
- One safe retry is allowed only for connection failure before any response;
  GET is read-only and uses the same request ID.
- SIMS stores only complete successful public projections as last-known-good.
- Fresh cache should be short enough for payment visibility, recommended two
  minutes. Stale fallback expires at 15 minutes.
- Cache key includes parent identity, normalized period, page/cursor, limit, and
  contract version.
- Feature-flag disable and cache clear are operational controls; they do not
  mutate finance records.

## Backward Compatibility

- Existing `GET /api/parent/get-invoices` remains unchanged for Pending and
  payment screens.
- Existing parent bearer-token behavior and response-code normalization remain
  unchanged.
- Existing Ripple staff statement route preserves its external response shape
  while moving calculation into the canonical engine.
- The new app uses only contract v1 fields and handles additive unknown fields.
- Breaking changes require `/v2` or a negotiated `contract_version` change.
